Evidence Before Claims

기술 이름보다 무엇을 확인했고 무엇이 아직 가설인지 구분합니다. 특히 성능과 관련된 표현은 같은 조건의 Baseline과 개선 후 측정값이 있을 때만 사용합니다.

01

Baseline 먼저 기록

기기·빌드·해상도·카메라·오브젝트 수·실행 경로를 고정하고, Warm-up 이후 구간을 비교 기준으로 남깁니다.

02

변수 하나만 변경

여러 변경을 한꺼번에 성과로 묶지 않습니다. 재현 → 측정 → 가설 → 단일 변경 → 재측정 순서로 원인을 좁힙니다.

03

결과와 한계 함께 공개

Profiler나 Benchmark가 없다면 ‘최적화’라고 단정하지 않습니다. 확인된 구현, 기대 효과, 추가 검증 항목을 분리합니다.

Felheim

3D 액션 Unity, C#

2인 팀 프로젝트 | 클라이언트 개발 전반 담당

완료 (2026.05.28 - 2026.06.24)

Behavior Tree로 적 행동을 노드 단위로 나누고, 던전 진입 시 전체 몬스터를 생성하던 구조를 문 트리거 기반 Addressables 비동기 로드 방식으로 변경한 2인 프로젝트입니다.

문제

던전 진입 시 몬스터가 함께 생성되고, 적 행동 규칙과 수치 조정 지점이 기능별로 흩어져 있었습니다.

제약

2인·4주 프로젝트에서 기존 AI 패키지와 Unity 생명주기를 고려하며 담당 범위 안에서 구조를 변경해야 했습니다.

판단

행동을 노드와 데이터로 분리하고 로드 시점을 문 상호작용으로 늦췄습니다. 성능 효과는 Baseline 측정 전까지 단정하지 않습니다.

IMPLEMENTATION DEBUGGING

구현 오류를 재현하고 수정한 과정

CASE 01 · Behavior Tree 공격 쿨타임
오류

Blackboard 값이 예상대로 동기화되지 않아 적의 공격 쿨타임이 무시됐습니다.

원인 확인

공격 노드의 조건과 값 갱신 시점을 따라가며 컴포넌트가 사용할 Blackboard 참조 지점을 좁혔습니다.

수정

외부 패키지 소스를 직접 변경하지 않고 BehaviorGraphAgent의 BlackboardReference를 컴포넌트 레벨에서 참조하도록 분리했습니다.

재검증

동일한 전투 흐름을 반복해 설정한 공격 주기가 적용되는지 다시 확인했습니다.

CASE 02 · Addressables 생성 상태
오류

로딩 중 오브젝트 비활성화와 코루틴 중단이 겹치며 몬스터 생성 상태가 꼬였습니다.

원인 확인

Addressables 완료 시점과 Unity 오브젝트 생명주기가 충돌하는 재현 경로를 확인했습니다.

수정

렌더러·충돌체 제어와 생성 완료 콜백을 분리하고 중복 생성 방지 조건을 추가했습니다.

재검증

같은 던전 진입 경로에서 로딩 완료와 생성 상태가 끝까지 이어지는지 반복 확인했습니다.

🎯 직접 담당한 기능

  • • 데이터 구조: Scriptable Object 카탈로그로 아이템·버프 데이터를 분리하고 Observer Pattern으로 PlayerStatus와 연동
  • • 적 행동: 추적·도망·공격·순찰 노드와 조건 분기를 사용하는 Behavior Tree 구성
  • • 로드 구조 변경: 문 상호작용 시 해당 구역 몬스터를 Addressables로 비동기 생성하도록 진입 시점을 분리
  • • 피드백 연출: Auto-Hide Bubble, 제단 환경 변화, 보스 스킬 구간 Audio Ducking 구현
확인된 구현

문 트리거, 구역별 비동기 생성, 담당 기능 시연 영상과 발표 자료가 있습니다.

IDLE CITY

방치형 시뮬레이션 Unity, C#

5인 팀 프로젝트 | UI/UX · 건설 제어 · HUD · 프리팹 폴리시

완료 (2026.07 - 2026.08)

차량 이동 → 코인 획득 → 건물 해금 → 도시 확장으로 이어지는 방치형 도시 건설 시뮬레이션입니다. 저는 건설 입력과 시각 피드백을 분리하고, 사용자가 클릭 전에 결과를 예측할 수 있는 UI/UX를 구현했습니다.

문제

빠른 드래그에서 도로가 끊기고 오래된 입력 요청이 쌓였으며, 배치 가능 여부를 클릭 전에 판단하기 어려웠습니다.

제약

5인 팀의 공용 Canvas·Prefab·건설 데이터와 연결하면서 기존 기능의 입력 흐름을 함께 유지해야 했습니다.

판단

입력 위치 보간, 오래된 요청 폐기, 초록·빨강 Ghost와 UI Raycast 검사를 조합해 건설 결과를 예측할 수 있게 했습니다.

IMPLEMENTATION DEBUGGING

빠른 드래그에서 도로가 끊기는 오류

CASE 01 · 연속 건설 입력
오류

드래그 속도가 빨라지면 입력 프레임 사이 타일이 누락되어 도로가 끊기고 오래된 요청이 남았습니다.

원인 확인

이전 입력과 현재 입력의 그리드 좌표가 멀어질 때 중간 셀을 검사하지 않는 흐름을 확인했습니다.

수정

두 좌표 사이의 셀을 보간해 경로를 채우고, 새 입력과 멀어진 오래된 건설 요청을 폐기했습니다.

재검증

같은 드래그 경로를 다시 실행해 도로 연결을 확인하고 UI 위 입력은 Raycast 검사로 차단했습니다.

직접 구현한 사용자 경험

  • 연속 건설: 이전·현재 입력 위치 사이 타일을 보간해 빠른 드래그에서도 도로가 끊기지 않도록 개선
  • 입력 지연 제어: 현재 포인터와 멀어진 오래된 요청을 폐기해 배치 지연 누적 방지
  • 예측 가능한 피드백: 초록·빨강 Ghost와 UI Raycast 검사로 배치 가능 여부와 입력 대상을 명확히 전달
  • 상태 규칙 통일: 도로·일반 건물의 건설 모드 종료 조건과 정보창 닫기 입력을 일관되게 정리

팀 QA에서 검증한 게임 규칙

도로를 무작정 늘리면 교통 성과가 높아지던 문제를 발견하고, 게임의 핵심 재미와 지표가 어긋난 원인을 팀 단위로 검토했습니다.

  • 원인: 차량의 실제 도착과 수익·성과 지표가 연결되지 않음
  • 수정: 실제 도착을 수익 기준으로 통일하고 혼잡도를 타일별로 시각화
  • 결과: 도로 도배가 아닌 교통 흐름 개선이 수익으로 이어지도록 게임 규칙 정리
