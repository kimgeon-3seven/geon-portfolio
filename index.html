02

WORKING RULE

성능 표현과 검증 기준

기술 이름보다 확인한 사실과 아직 측정하지 않은 항목을 구분합니다. 성능 효과는 같은 조건의 Baseline과 변경 후 측정값이 있을 때만 결과로 기록합니다.

  1. 01
    Baseline 기록

    기기·빌드·해상도·카메라·오브젝트 수·실행 경로를 고정하고 Warm-up 이후 구간을 비교 기준으로 남깁니다.

  2. 02
    변수 하나만 변경

    재현 → 측정 → 가설 → 단일 변경 → 재측정 순서로 원인을 좁힙니다.

  3. 03
    결과와 한계 분리

    Profiler나 Benchmark가 없다면 성능 향상을 단정하지 않고 구현 변경과 추가 검증 항목을 나눠 기록합니다.

QA 관점재현 조건과 수정 후 확인 기록

기대 결과와 실제 결과, 재현 절차, 수정 내용, 동일 조건의 재검증을 한 흐름으로 배치했습니다.

클라이언트 개발 관점구현 구조와 측정 여부의 분리

Unity·C# 구현 범위와 선택 이유는 기록하고, Baseline이 없는 성능 효과는 측정 전 항목으로 표시했습니다.

게임 기획 관점규칙과 플레이 결과의 비교

사용자 입력, UI 피드백, 보상 구조, 팀 QA에서 확인한 문제를 프로젝트별 플레이 흐름에 연결했습니다.

확인된 기술 범위Unity / C# / Behavior Tree / Addressables / Scriptable Object / Observer Pattern / DOTween

Felheim

Behavior Tree · 데이터 구조 · 구역별 로드 · 피드백 연출

2026.05.28 — 06.24
완료

개발 환경
Unity, C# / Windows
담당 범위
적 행동, 아이템·버프 데이터, 구역별 몬스터 생성, 피드백 연출
확인 자료
1분 15초 트레일러, 3분 19초 담당 기능 시연

Behavior Tree로 적 행동을 노드 단위로 나누고, 던전 진입 시 전체 몬스터를 생성하던 구조를 문 트리거 기반 Addressables 비동기 로드 방식으로 변경한 프로젝트입니다.

문제

던전 진입 시 몬스터가 함께 생성되고, 적 행동 규칙과 수치 조정 지점이 기능별로 흩어져 있었습니다.

제약

2인·4주 프로젝트에서 기존 AI 패키지와 Unity 생명주기를 고려하며 담당 범위 안에서 구조를 변경해야 했습니다.

구현

행동을 노드와 데이터로 분리하고 로드 시점을 문 상호작용으로 늦췄습니다. 성능 효과는 Baseline 측정 전까지 결과로 단정하지 않았습니다.

IMPLEMENTATION DEBUGGING

구현 오류를 재현하고 수정한 과정

CASE 01
Behavior Tree 공격 쿨타임
  1. 오류

    Blackboard 값이 예상대로 동기화되지 않아 적의 공격 쿨타임이 무시됐습니다.

  2. 원인 확인

    공격 노드의 조건과 값 갱신 시점을 따라가며 컴포넌트가 사용할 Blackboard 참조 지점을 좁혔습니다.

  3. 수정

    외부 패키지 소스를 직접 변경하지 않고 BehaviorGraphAgent의 BlackboardReference를 컴포넌트 레벨에서 참조하도록 분리했습니다.

  4. 재검증

    동일한 전투 흐름을 반복해 설정한 공격 주기가 적용되는지 다시 확인했습니다.

CODE EVIDENCE
Blackboard 값을 읽는 위치 변경

CheckCooldownCondition.cs · Unity Version Control · /main/develop/Geon · Changeset 74 → 164

외부 Behavior 패키지는 수정하지 않고, 조건 노드가 실제 Agent의 BlackboardReference에서 같은 이름의 값을 읽도록 변경했습니다.

CASE 02
Addressables 생성 상태
  1. 오류

    로딩 중 오브젝트 비활성화와 코루틴 중단이 겹치며 몬스터 생성 상태가 꼬였습니다.

  2. 원인 확인

    Addressables 완료 시점과 Unity 오브젝트 생명주기가 충돌하는 재현 경로를 확인했습니다.

  3. 수정

    렌더러·충돌체 제어와 생성 완료 콜백을 분리하고 중복 생성 방지 조건을 추가했습니다.

  4. 재검증

    같은 던전 진입 경로에서 로딩 완료와 생성 상태가 끝까지 이어지는지 반복 확인했습니다.

CODE EVIDENCE
코루틴이 끝난 뒤 문 오브젝트 비활성화

DungeonDoor.cs · Unity Version Control · Changeset 168 최초 반영 코드

이 파일은 최초 저장된 Changeset 168부터 수정 형태로 포함되어 있습니다. 왼쪽은 과거 리비전이 아니라 확인한 오류 흐름을 단순화한 의사 코드입니다.

직접 담당한 기능

  • 데이터 구조Scriptable Object 카탈로그로 아이템·버프 데이터를 분리하고 Observer Pattern으로 PlayerStatus와 연동
  • 적 행동추적·도망·공격·순찰 노드와 조건 분기를 사용하는 Behavior Tree 구성
  • 로드 구조문 상호작용 시 해당 구역 몬스터를 Addressables로 비동기 생성하도록 진입 시점을 분리
  • 피드백 연출Auto-Hide Bubble, 제단 환경 변화, 보스 스킬 구간 Audio Ducking 구현

5인 팀 · 6주 · 방치형 시뮬레이션

IDLE CITY

건설 입력 · 배치 피드백 · HUD · 공용 Prefab 연결

2026.07 — 08
완료

개발 환경
Unity, C# / Windows
담당 범위
건설 입력, Ghost 피드백, HUD, 공용 Canvas·Prefab 연결
확인 자료
1분 트레일러, 4분 30초 기능 영상, 공개 저장소

차량 이동 → 코인 획득 → 건물 해금 → 도시 확장으로 이어지는 방치형 도시 건설 시뮬레이션입니다. 건설 입력, 배치 상태 Ghost, UI Raycast, HUD와 공용 Prefab 연결을 담당했습니다.

문제

빠른 드래그에서 도로가 끊기고 오래된 입력 요청이 쌓였으며, 배치 가능 여부를 클릭 전에 판단하기 어려웠습니다.

제약

5인 팀의 공용 Canvas·Prefab·건설 데이터와 연결하면서 기존 기능의 입력 흐름을 유지해야 했습니다.

구현

입력 위치 보간과 오래된 요청 폐기를 적용하고, 초록·빨강 Ghost로 클릭 전 배치 가능 여부를 표시했습니다.

IMPLEMENTATION DEBUGGING

빠른 드래그에서 도로가 끊기는 오류

CASE 03
연속 건설 입력
  1. 오류

    드래그 속도가 빨라지면 입력 프레임 사이 타일이 누락되어 도로가 끊기고 오래된 요청이 남았습니다.

  2. 원인 확인

    이전 입력과 현재 입력의 그리드 좌표가 멀어질 때 중간 셀을 검사하지 않는 흐름을 확인했습니다.

  3. 수정

    두 좌표 사이의 셀을 보간해 경로를 채우고, 새 입력과 멀어진 오래된 건설 요청을 폐기했습니다.

  4. 재검증

    같은 드래그 경로를 다시 실행해 도로 연결을 확인하고 UI 위 입력은 Raycast 검사로 차단했습니다.

CODE EVIDENCE

직접 구현한 기능

  • 연속 건설이전·현재 입력 위치 사이 타일을 보간해 빠른 드래그에서 누락된 중간 셀을 연결
  • 입력 지연 제어현재 포인터와 멀어진 오래된 요청을 폐기해 배치 지연 누적 방지
  • 상태 피드백초록·빨강 Ghost로 배치 가능 여부를 클릭 전에 표시하고 UI 위 입력은 Raycast 검사로 차단
  • 규칙 통일도로·일반 건물의 건설 모드 종료 조건과 정보창 닫기 입력을 일관되게 정리

팀 QA에서 확인한 규칙

  • 확인차량 도착 여부와 관계없이 도로 수가 늘면 교통 성과가 높아짐
  • 원인차량의 실제 도착과 수익·성과 지표가 연결되지 않음
  • 수정실제 도착을 수익 기준으로 통일하고 혼잡도를 타일별로 시각화
